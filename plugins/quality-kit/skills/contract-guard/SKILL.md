# Keep the contract true

The contract is what clients build against. It says what the code does now, and `qk` says whether that breaks them. A break is the person's choice, made knowingly: your part is to make it visible.

`quality.yaml` is guarded: read it with Read, and run each `qk` command on its own.

## 1. Find the contract

Read `contracts` in `quality.yaml`: `openapi`, `asyncapi` and `odcs` are lists of globs. Then search the repository for contract files it does not list.

No contract covers what changed: say so, write none, and finish with how to add one, from [references/contracts.md](references/contracts.md). A contract made up from one diff would state facts nobody checked.

## 2. Read the change

The change is everything since the branch left the default branch, committed or not:

```sh
git diff "$(git merge-base <default branch> HEAD)" -- <file>
```

Done when you can say what a client now sends or gets back that it did not before, and what it no longer does.

## 3. Make the contract say what the code does

- **A generated contract** (under `generated` in `quality.yaml`, or opening with a `generated by` line): run its command. Your Edit and Write stay off the file.
- **Otherwise** edit it. Change what the diff changed, with the names, types and required fields the code shows.

The contract follows the code, also when that breaks clients. A contract that hides a break is worse than the break.

## 4. Let `qk` compare

```sh
qk check --format claude
```

Read what it says about QK030:

- **No QK030 line:** the change is compatible. Go to section 6.
- **`QK030 fail`**, or a QK030 warning that starts with `possibly breaking`: go to section 5.
- **QK030 is on the `Skipped:` line**, or the contract is AsyncAPI or ODCS, which `qk` does not compare yet: no automated comparison ran. Say so, with the reason `qk` gave. Then give your own reading of the diff, named as your reading, and treat a break you see as section 5 does.

## 5. A break is the person's decision

Tell the person what breaks, in the words `qk` printed, and the ways to stay compatible that fit, from the reference. Ask which they intend, and stop.

The waiver comes after their answer. Only when they confirm the break is intended, draft `qk waiver add QK030` as the reference shows, for them to approve. Run it only after a yes and the names to record.

If the Stop hook sends you back for the finding, give the finding and the question again in full, and stop.

## 6. Write the note for clients

For a compatible change, write what changes for clients where the repository keeps its changes: under the unreleased heading of `CHANGELOG.md` or `CHANGES.md`. Without such a file, put the note in your report, for the pull request. For a break, the note waits for the person's decision.

## 7. Report

1. What you changed in the contract, and the part of the diff it rests on.
2. What `qk` said about QK030, as printed, or that no comparison ran and why.
3. The note for clients, and where it is.
4. The question that waits for the person, if there is one.
