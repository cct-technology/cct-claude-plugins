# Changelog

## Unreleased

### Fixed

- The PreToolUse hook tells reads from writes. A shell command that only reads `quality.yaml` or `.quality/` (`cat`, `grep`, `ls`, `test -f`, `diff`, `git diff`, `Get-Content` and the like) no longer asks a person, and neither do `git add`, `git commit`, `git tag` and `git branch`. Before, any command that named one of them asked, with a prompt that said an exception was being changed. Only a plain read passes, and the hook lists what that is: every command on the line is one that only reads, or one of `qk`, `cd`, `which`, `type` and `command -v` beside it; every word is written out in full, with no variable and no substitution other than `$(git merge-base ...)`; the commands are joined by `;`, `&&`, `||`, `|`, `if`, `( )` or `{ }`; and no output goes to the path. Everything else that names one of them still asks, so some reads ask: `cat "$HOME/repo/quality.yaml"`, `sed -n 1,5p quality.yaml`, a read beside `make`. The prompt for such a line says it is not a plain read and that a read on its own line needs no approval, so Claude reads again by itself when nobody approves. Bash lines are parsed, with the parser of `shfmt` (`mvdan.cc/sh`, a new dependency). PowerShell lines are not: the same rules are applied to their text. The two names now count in any case, as Windows and macOS read them, so `QUALITY.YAML` asks. How-to: `docs/how-to/work-with-the-hooks.md`.
- The reusable workflow `.github/workflows/quality.yml` runs `qk check` once, where it ran twice. The pull request comment, the SARIF and the job result now come from the same run, and each command under `generated` runs once. Before, a generator that wrote a file not listed under `generated` lost its QK020 warning in the comment, and the comment could show a QK010 finding on that file which the job had not failed on.

### Added

- QK060 (`supply-chain.dependencies`): each dependency a change adds or moves to another version, in `package.json`, `go.mod`, `composer.json`, `Cargo.toml`, `pyproject.toml`, `Pipfile` or `requirements*.txt`, is looked up in its public registry (npm, the Go module proxy, Packagist, crates.io, PyPI). It must exist, its version must have been published at least 14 days ago, it must not be deprecated, abandoned or yanked, and its licence must be MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC, 0BSD or Unlicense; one allowed licence of a choice is enough. The version is the one the lockfile holds (`package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `composer.lock`, `Cargo.lock`, `poetry.lock`, `uv.lock`, `Pipfile.lock`), so an upgrade that only changes the lockfile, as after `npm update`, is checked too. Without a lockfile it is the version the manifest names when it names one exactly; for a range it is the newest release, which is what an install may fetch. Only what a manifest names is checked, not the dependencies of dependencies. Go modules have no licence data, so only their licence is left unchecked. A registry that cannot be reached skips the check and never fails it. Answers are cached for 24 hours. It uses the network, so it runs with `qk check --full` and in CI, not when Claude finishes. A package from a private registry reads as missing: waive it by name. Text a registry holds (a deprecation note, a licence) is cut to one short line before it goes into a finding. Enforced from silver. How-to: `docs/how-to/check-dependencies.md`.
- `qk waiver add --package <name>[@version]` limits a waiver to findings about one dependency, at one version or at every version. Another package in the same manifest is still checked. The approval in the exceptions log names the packages, so a waiver widened by hand does not apply.
- `qk deps verify <ecosystem> <name>[@version]` runs the same four checks for one package before you add or upgrade it, for `npm`, `go`, `composer`, `cargo` or `pypi`. Exit code 1 means a finding; a registry that cannot be reached prints `skipped:` and exits 0.
- `README.md` at the repository root: what Quality Kit is, every check, skill, hook and command with a link to its guide, and how to install the plugin in a repository. Parts that are specified and not built yet are marked `Coming`: QK060 with `qk deps verify`, and the two hooks that guard generated files and package installs.
- Tutorial `docs/tutorials/first-run.md`: install the plugin in a practice repository, let Claude set it up, fix the first finding, and watch Quality Kit send Claude back to update a doc.
- `docs/how-to/README.md` lists every how-to by goal, by skill and by check.
- Explanation pages under `docs/explanation/`: why `qk` decides and Claude writes, why Quality Kit fails open, and how modes and maturity work.
- `docs/how-to/get-the-qk-binary.md` says how to install `qk` yourself before the first release and while the repository is private: `bin/qk` cannot download from a private repository.
- A test checks the README and the docs: every link leads to a file and a heading, the how-to index lists every how-to, and the README names every rule, with the level it blocks from, and every skill.
- Skill `threat-model` writes a short threat model for a feature, when a new spec is added, when a change adds a trust boundary, when Quality Kit reports QK040 or when you ask. It finds the trust boundaries in the spec and the code, walks STRIDE at each, and writes `docs/security/threat-models/<name of the spec>.md` (or the folder under `security.threat_models`) with `spec:` in its frontmatter, so QK040 finds it. Each threat has a mitigation, a status (`in place` only when the code shows it, otherwise `to do`) and the ISO/IEC 27001:2022 Annex A control it serves. A feature that uses an LLM also gets the ten risks of the OWASP Top 10 for LLM applications (2026 edition), each with a row or a reason why it does not apply. Threats still to do become a checklist in the file; with Linear connected, Claude files the ones you name as issues, after you answer. It never marks a risk as accepted. The file keeps to two pages: at most 5 boundaries and 12 threats. How-to: `docs/how-to/write-a-threat-model-with-claude.md`.
- Skill `test-plan` writes the plan people follow when they test a release by hand, when you say a release or an epic is ready for testing or ask for a UAT plan. It reads what the release holds since the last tag and who uses it, and writes `docs/testing/uat/<release>.md` (or the folder under `testing.uat_dir`): steps for each role whose work changes, one to three exploratory charters, and the security acceptance checks (wrong role, another tenant, expired session), with a `Status` and an `Evidence` cell in every row. Roles and labels come from the repository; what an automated test already checks is left out and named in the report. Every row starts as `todo`: people run the plan, Claude does not. A release that shows a person nothing new gets a plan with one section, **Nothing to test by hand**, and the tests that cover it. The plan keeps to two pages. How-to: `docs/how-to/write-a-uat-plan-with-claude.md`.
- Skill `contract-guard` keeps API, event and dataset contracts true to the code, when a change alters what a client sends or gets back, when Quality Kit reports QK030, or when you ask. It updates the OpenAPI, AsyncAPI or ODCS file from the diff, has `qk check` compare it with the base, and writes the note for clients under the unreleased heading of `CHANGELOG.md` or `CHANGES.md`. When the change breaks clients it says what breaks, lists the ways to stay compatible and asks what is intended; it drafts a waiver only after the person confirms the break, and never runs one on its own. When no comparison ran (no `oasdiff`, or an AsyncAPI or ODCS contract), it says so and gives its own reading as a reading. In a repository with no contract it writes none and says how to add one. How-to: `docs/how-to/keep-contracts-true-with-claude.md`.
- Skill `docs-sync` brings the docs in line with what a branch changed, when Quality Kit reports QK010 or QK020 or when you ask. It reads the findings from `qk check --full --format claude` and the diff since the branch left the default branch. For a generated file it runs the generator and never edits the file. For a change a reader would notice it updates the how-to or explanation, or writes the page. Tutorials that walk through what changed keep their steps and get a `Re-run needed` mark under the title. For a change a reader cannot notice it writes no docs and proposes `qk docs-impact none` with a reason, for a person to approve; it does not run the command on its own. How-to: `docs/how-to/update-docs-with-claude.md`.
- Skill `quality-init` sets a repository up in one conversation. It asks for data class, maturity and replaced tools, leaving out what the request already said, and runs `qk init`. It then fills in `quality.yaml` where the repository shows the fact (`docs.impact_map`, `generated`, `contracts.openapi`, `security.specs_dir`), runs `qk check`, and hands over what is left for a person. In a repository that already has a `quality.yaml` it does not run `qk init` again: it shows what `qk check` finds. Its eval cases are under `plugins/quality-kit/evals/`. How-to: `docs/how-to/set-up-quality-kit-with-claude.md`.
- `qk init` sets a repository up for Quality Kit. From `--data-class`, `--maturity` and `--replaces` it writes `quality.yaml`, a `README.md` in each docs folder the manifest names (the four Diátaxis folders, threat models and UAT plans), and the line `.quality/exceptions-log.jsonl merge=union` in `.gitattributes`, so two branches that each record an exception merge without a conflict. When the `origin` remote is on GitHub, it also writes a `CODEOWNERS` stub that names `/.quality/` and `/quality.yaml`, unless GitHub already reads a `CODEOWNERS` file, and a CI workflow that calls the reusable workflow at the tag of the `qk` that ran. It then prints the ruleset setting that makes GitHub require a person's review of those two paths. On another host, or without an `origin` remote, it writes the core files only and says so. It names the stack it finds: Go, Node.js, PHP, Rust or Python. A file that exists is never overwritten: it is reported as skipped, and a second run changes nothing. How-to: `docs/how-to/set-up-quality-kit-in-a-repository.md`.
- `qk check --sarif <file>` also writes the report as SARIF to a file, whatever `--format` prints, so one run gives both.
- QK110 (`ownership.codeowners`): each file and folder at the top of the repository has an owner in `CODEOWNERS`. The file is read where the host of the `origin` remote reads it: GitHub (`.github/`, the root, `docs/`) or GitLab (the root, `docs/`, `.gitlab/`), first found first. Patterns are matched as the host matches them and the last matching line wins, so a later line without owners is a finding. A folder is owned when a new file in it would get an owner. On another host, or without an `origin` remote, the check is skipped with the reason. With `--changed`, only top-level paths the change adds are checked, unless the change touches `CODEOWNERS`. It needs no configuration. Enforced from gold. How-to: `docs/how-to/give-every-path-a-code-owner.md`.
- QK061 (`supply-chain.lockfile`): every dependency manifest git tracks (`package.json`, `go.mod`, `composer.json`, `Cargo.toml`, `Pipfile`, and `pyproject.toml` with Poetry or uv) that declares dependencies needs its lockfile in git, and when its dependencies change, the lockfile must change in the same change set. A workspace lockfile in a parent folder counts. Other edits to a manifest need nothing. Python with only `requirements.txt` is skipped with the reason. It needs no configuration and never runs a package manager. With `--changed`, only manifests and lockfiles in the change set are looked at. Enforced from silver. How-to: `docs/how-to/keep-lockfiles-in-step.md`.
- QK040 (`security.threat-model`): each Markdown file added under `security.specs_dir` in `quality.yaml` needs a threat model under `security.threat_models` (default `docs/security/threat-models`). A threat model belongs to a spec when it has the same file name, or when its frontmatter has `spec:` with the spec's path. Editing or moving a spec needs nothing. Without a `quality.yaml`, `docs/specs` is checked if it exists. Enforced from gold. How-to: `docs/how-to/require-a-threat-model-for-a-new-spec.md`.
- `setup` input for the reusable workflow `.github/workflows/quality.yml`: shell commands that run in the repository root before `qk check`, so generators (QK020) and `oasdiff` (QK030) have what they need in CI. A command that fails stops the setup and fails the job, and the pull request comment says qk did not run. Without the input, the workflow behaves as before. This repository's CI uses it to install `oasdiff`.
- QK030 (`contracts.breaking`): each changed file matching `contracts.openapi` in `quality.yaml` is compared with its version at the base, using `oasdiff`. A change that breaks clients is a finding; one oasdiff cannot confirm is a warning marked `possibly breaking`. A deleted contract fails, a new one passes, and a renamed one is compared with its old path. Without `oasdiff` on `PATH` the check is skipped with how to install it. Enforced from silver. How-to: `docs/how-to/catch-breaking-api-changes.md`.
- QK020 (`generated.current`): each file under `generated` in `quality.yaml` equals what its `cmd` writes, ignoring line endings. The command runs from the repository root without a shell. Afterwards the files under `generated` are put back; any other file that changed during the run is left as it is and named in a warning, since qk cannot tell the command's changes from a person's. A generator that fails is a finding with its output; one that is not installed skips the check. Enforced from silver.
- `qk check --full` runs slow checks such as QK020. They also run when `CI=true`, and are skipped otherwise. The Stop hook never runs them.
- Reusable GitHub Actions workflow `.github/workflows/quality.yml`. It installs the checksum-verified `qk` release, runs `qk check` against the pull request's base, and keeps one comment on the pull request up to date. It also keeps the SARIF as an artifact, and uploads it to code scanning when asked. The job fails when an enforced check fails or the downloaded `qk` does not match its checksum; other problems with Quality Kit only warn. This repository's CI now runs it.
- `qk check --format sarif` writes SARIF 2.1.0. Waived findings are results with an `external` suppression giving the waiver reason, and checks that did not run are notifications.
- Hooks. When a session starts, Claude gets the `qk context` summary. When Claude tries to finish, `qk check --changed` runs: enforced failures send Claude back with the findings, at most twice in a row, then the stop is allowed with "Quality Kit: unresolved findings, handing over to a human". Advisory findings and checks that could not run are shown to the person. The exception guard asks a person before Claude records an exception or changes `.quality/` or `quality.yaml`.
- `qk hook session-start` and `qk hook stop`. Any `qk hook` error is a warning on stderr with exit 0, including a hook this `qk` does not have.
- When `bin/qk` cannot find or download `qk`, the session-start hook also shows the person a message, because Claude Code hides stderr from a hook that exits 0.
- `qk context` prints a short summary for the start of a session: maturity, which checks are enforced or advisory, open findings per check, and waivers ending within 14 days. At most 30 lines; exits 0 even when an enforced check fails. Slow checks (QK020, QK060) are left out and named.
- `bin/qk` in the plugin finds the `qk` binary its version needs: on `PATH`, in the cache, or by downloading the matching release and verifying its checksum. If none works it warns on stderr and exits 0.
- Release pipeline: pushing a version tag publishes archives for darwin, linux and windows on amd64 and arm64, with `checksums.txt`. The release fails when the tag does not match `version` in `plugin.json`.
- This repository checks itself: `quality.yaml` at silver, CODEOWNERS, and `qk check` on every pull request.
- QK010 (`docs.impact`): when a changed file matches `paths` in `impact_map`, a file matching that entry's `docs` must change too. Enforced from silver.
- `qk docs-impact none --reason --approved-by` records a person's approval that a branch's change needs no docs, in a note and in the exceptions log. A hand-written or later-edited note does not count.
- Exceptions need a person's approval and are logged. `qk waiver add` requires `--approved-by` and appends to `.quality/exceptions-log.jsonl`; a waiver with no matching line does not apply, and QK100 fails it. `qk hook pre-tool-use` makes Claude Code ask a person before Claude records an exception or changes `.quality/` or `quality.yaml`.
- Waivers in `.quality/waivers.yaml`: `qk waiver add <rule-id> --reason --owner --expires --approved-by [--path]` records an agreed, owned, time-limited exception. A waived finding no longer blocks and is listed as waived in every output format; a rule with only waived findings reports `pass`. The JSON report gains `waived` on rule results and in the summary.
- QK100 (`waivers.valid`): every waiver has a reason, an owner, a valid end date and a matching approval in the log, and has not expired. An expired, incomplete or unapproved waiver never applies. A waiver for a rule this `qk` does not have is a warning. QK100 cannot be waived.
- `qk check` finds the repository root from any subfolder and computes what changed: files changed between the merge-base with the default branch (`origin/HEAD`, then `main`, then `master`) and the working tree, including uncommitted and untracked files. Outside git, checks that need this are skipped with the reason.
- `qk check --base <ref>` compares against the merge-base with another ref; a ref that names no commit exits 2. `qk check --changed` limits whole-repo checks to changed files.
- `quality.yaml` manifest, version 1, validated against `plugins/quality-kit/schemas/quality.schema.json`. `maturity` and `modes` now set each check's mode; with no manifest, every check stays advisory. An invalid manifest is treated as bronze, so QK001 blocks.
- QK001 (`manifest.valid`): `quality.yaml` is valid. Each problem names the key path and what is allowed. A `modes` key that matches no check is a warning, so a manifest written for a newer `qk` does not block an older one.
- Generated `docs/reference/manifest.md` listing every key, and a how-to for configuring `quality.yaml`.
- `qk check --format claude` ends with a `Skipped:` line naming each check that did not run and why, so a check that could not run never reads as "no findings".
- `qk check --format text|json|claude` runs every registered rule and reports `pass`, `warn`, `fail` or `skipped`. Exit code 1 means an enforced rule failed; 2 means a usage error.
- Modes: `maturity` sets each rule's default mode; `modes` overrides it per check key. Advisory failures are reported as warnings. A rule that crashes is reported as skipped (fail open).
- `qk explain <rule-id>` prints what a rule checks and how to fix it.
- Generated rule reference at `docs/reference/rules.md` (`go run ./cmd/gen-docs`); CI fails when it is out of date.
- `qk version` prints the qk version and the `quality.yaml` schema version it reads.
- Marketplace `cct-claude-plugins` with the `quality-kit` plugin (no components yet).
- CI runs `go vet` and `go test` on Linux, macOS and Windows.
